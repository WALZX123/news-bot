# 运维与恢复

## 日常检查

`python -B main.py --check-db` 只读检查表结构、迁移状态、计数和未知送达批次。`succeeded` 表示本次实际完成；`partial`、`failed`、`waiting` 和 `busy` 分别说明部分失败、失败、等待窗口和已有任务占用。空源或没有新新闻不阻止独立报告检查。

AI 调用的模型、提示版本、用量和输出预算随分析保存。可通过 `ai` 配置控制 Token、调用数和总时限。评分不完整时保留待处理记录。

## 送达未知

外部发送和本地数据库无法组成一个原子事务。“远端收到但客户端超时”需要人工核对。先用 `--check-db` 找到未知批次，核对钉钉群里的实际消息、时间、标题和批次新闻 ID。

只有已经拿到可靠结果时才执行以下其中一个命令。占位符须换成真实批次 ID；note 填回执编号或核验记录，不填任何密钥。

```powershell
python -B main.py --resolve-batch BATCH_ID --delivery-outcome confirmed-sent --receipt-note '平台回执编号及核验记录'
python -B main.py --resolve-batch BATCH_ID --delivery-outcome confirmed-not-sent --receipt-note '已确认未送达的依据'
```

前者补记成功回执和该批次的实际新闻状态；后者允许后续正常流水线复用分析重试。这两个命令自身均不发送消息，也拒绝重复/冲突处理已经结案的批次。证据仍不清楚时继续保留 unknown。

## 备份与恢复演练

暂停写入后，备份到私密路径，选择全新文件名；程序拒绝覆盖既有备份：

```powershell
python -B tools/database_snapshot.py --backup backups/news-before-upgrade.json
```

备份包括建表定义和数据，不含连接密码。配置文件需单独保存在私密备份中。MySQL 8/InnoDB 一致性快照覆盖同一事务的数据；迁移等 DDL 期间不要同时备份。

恢复只允许**全新且不同于当前配置的库名**，不会 DROP 或覆盖现有库：

```powershell
python -B tools/database_snapshot.py --restore backups/news-before-upgrade.json --new-database news_bot_restore_check
```

只恢复自己生成并保管的可信备份，工具不是上传文件执行接口。先在新库核对表数、行数、关键状态、批次/回执和时间语义，再决定切换配置。升级前旧版快照仍需按旧时区初始化。恢复失败时保留目标库用于核验，不会自动删除用户库。

## 配置保存失败

保存先做完整校验，持有排他 `.lock`，写入独立字节备份，最后原子替换；编辑器摘要冲突要求重载。进程在保存过程中崩溃可能留下 `.lock`。先确认没有保存任务或其他编辑进程，备份当前文件后再移走这个**确切锁文件**，不能递归清理目录。不要为了恢复而删 `.bak`。

## 升级和灰度

1. 停止旧调度器和 Web。旧版没有新锁，不能让它与迁移同时运行。
2. 备份代码、配置、数据库，并核对原时区。初始化会保留旧记录和重复旧报告，用独立周期 ledger 管理新报告唯一性。
3. 在独立库运行迁移和故障回归；在原路径运行只读 `--check-db`。
4. 先仅启用 `--fetch-only`，检查源健康、入库和积压，不产生模型/推送副作用。
5. 确认模型费用和目标测试群后再运行一轮完整流程，核对群消息、成功历史与数据库 ID 一致，再恢复定时运行。

本次本地修复没有自动调用付费模型、向钉钉发送或启动长期调度器。真实模型稿件事实抽查、浏览器视觉验收与平台消息容量仍需对应运行证据。

## 回滚

先停止新进程，再从升级前文件备份恢复代码和配置。新表和附加列可以暂时保留，不必破坏性删除。不要把旧数据库快照直接覆盖在已发生新发送的库上，否则新回执丢失会导致再次发送。

故障期间优先暂停发送、保留批次/尝试记录并做只读核验。需要恢复数据时先恢复到新库，核对新旧成功回执后再切换。回滚不撤销已经发到外部群里的消息。
